## Idear
做一个能翻译多种文件或直接收文本输入的 Skill，供 AI Coding IDE 使用。
支持格式: .txt, .pdf, .docx, .md, .epub 等。
支持超大文件: 1000-2000 页。
支持直接输出成pdf,docx,或md，超大文件拆分多个输出。
建立评估标准，全部翻译完成后，或超长文本或文件部分翻译完成后，根据评估标准进行翻译质量审查并评分，如果达不到要求需要根据建议修改翻译直到达标

### 📋 新需求实现要点

1. **多格式输出**
   - 在 `output` 模块实现 PDF、DOCX、Markdown 输出
   - 配置文件中添加输出格式选项

2. **超大文件拆分**
   - 在 `chunking` 模块实现文件大小检测
   - 超过阈值时自动拆分为多个输出文件
   - 生成文件命名规则：`output_1.pdf`, `output_2.pdf` 等

3. **跨会话上下文保存**
   - 使用 `/save-session` 保存关键节点
   - 使用 `/resume-session` 恢复上下文
   - 确保 PRD 上下文在整个开发过程中保持一致

## 为什么恢复到 PRD 上下文

### 🎯 核心原因：PRD 是唯一真实来源

**PRD (Product Requirements Document)** 是整个项目的 **"唯一真实来源"** (Source of Truth)，包含了完整的产品需求、验收标准和业务逻辑。

### 🔍 详细解释

1. **需求一致性**
   - PRD 包含完整的功能需求、非功能需求和验收标准
   - 所有后续工作（架构设计、规划、实施）都基于 PRD
   - 恢复 PRD 上下文确保后续工作与原始需求保持一致

2. **跨会话连续性**
   - 项目开发可能跨越多个会话
   - 每次恢复工作时，需要确保从正确的需求起点开始
   - PRD 上下文包含了完整的需求背景，避免上下文丢失

3. **架构和规划的基础**
   - 架构设计 (`architect`) 是基于 PRD 进行的
   - 多 PR 规划 (`/blueprint`) 也是基于 PRD 的需求进行拆分
   - 即使完成了架构设计和规划，PRD 仍然是最终的验收标准

4. **实施阶段的参考**
   - 在实施阶段，开发者需要不断参考 PRD 来确保功能实现符合需求
   - 特别是在处理复杂功能时，PRD 是判断功能是否正确实现的依据

5. **避免需求偏差**
   - 长时间的开发过程中，可能会出现需求理解偏差
   - 定期恢复 PRD 上下文可以帮助开发者重新对齐原始需求

### 📊 上下文层次结构

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    上下文层次结构                                           │
│                                                                             │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  PRD 上下文 (核心需求)                                          │   │
│   │  ┌─────────────────────────────────────────────────────────────┐   │   │
│   │  │  架构设计上下文 (技术方案)                                   │   │   │
│   │  │  ┌─────────────────────────────────────────────────────┐   │   │   │
│   │  │  │  多 PR 规划上下文 (PR 拆分)                          │   │   │   │
│   │  │  │  ┌─────────────────────────────────────────────┐   │   │   │   │
│   │  │  │  │  详细计划上下文 (实施步骤)                      │   │   │   │   │
│   │  │  │  └─────────────────────────────────────────────┘   │   │   │   │
│   │  │  └─────────────────────────────────────────────────────┘   │   │   │
│   │  └─────────────────────────────────────────────────────────────┘   │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

- **PRD 上下文** 是最底层、最核心的上下文
- 上层上下文（架构、规划、实施）都是基于 PRD 上下文构建的
- 恢复 PRD 上下文可以确保整个开发过程的需求一致性

### 💡 实际应用场景

#### 场景 1: 多会话开发

```bash
# 会话 1: 产品和架构阶段
/prp-prd              # 创建 PRD
/save-session any-file-translator-prd
architect             # 架构设计
/blueprint any-file-translator "build translation skill"

# 会话 2: 实施阶段
/resume-session any-file-translator-prd  # 恢复 PRD 上下文
/prp-plan .claude/PRPs/prd/any-file-translator.prd.md  # 基于 PRD 生成计划
/prp-implement plan.md  # 执行计划
```

#### 场景 2: 需求变更

```bash
# 会话 1: 初始 PRD
/prp-prd
/save-session v1-prd

# 会话 2: 需求变更
/resume-session v1-prd  # 恢复原始 PRD
# 修改 PRD
/save-session v2-prd
```

### 🎯 总结

**恢复到 PRD 上下文** 是确保整个开发过程需求一致性的关键做法。无论经过了多少架构设计和规划步骤，PRD 始终是最终的需求来源和验收标准。

这种做法可以：
1. 避免跨会话开发时的需求偏差
2. 确保所有实施工作都基于原始需求
3. 提供清晰的需求参考点
4. 帮助开发者在复杂项目中保持方向

**一句话总结**: PRD 是项目的"指南针"，恢复 PRD 上下文确保开发始终朝着正确的方向前进。
